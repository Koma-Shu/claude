Chapter 1 — PHY & Wi-Fi (IEEE 802.11)

電源ON。すべての前に「電波の握手」— 物理層とWi-Fi

DHCPもARPも、その前にフレームを載せる「道」そのものがなければ始まりません。 物理層の仕事は 0/1 を電圧・光・電波の波形に変えること(無線ならOFDMやQAMといった変調)。 そしてWi-Fiでは、APと端末が4段階の接続儀式を済ませて初めてL2のリンクが張られます。

電波は「同時に1人しか話せない」— CSMA/CA: 無線は同じ周波数を全員で共有する半二重の世界。そこで各端末は 「①まず聞く(キャリアセンス) → ②静かならランダム時間待って送る → ③受信側からのACKフレームで成功確認」 という CSMA/CA(衝突回避)で譲り合います。互いに聞こえない端末同士がぶつかる 「隠れ端末問題」にはRTS/CTSという事前予約で対処。 一方、有線スイッチのポートは送受別線の全二重なので衝突自体が存在せず、 往年のCSMA/CD(衝突検出)は歴史的役目を終えています。

L1変調 — 1回の波に何ビット詰め込むか(QAMを触って理解する)

デジタル変調は、電波の位相と振幅の組み合わせを「点」として使い、どの点を打ったかでビット列を表します。 下のボタンで方式を切り替えてみてください。点が密になるほど1シンボルで運べるビット数は増えますが、 わずかなノイズで隣の点と誤認するため、要求されるSNR(信号対雑音比)が跳ね上がります。

世代の正体はほぼこれ: 11a/g=64-QAM、11n=64-QAM+MIMO、11ac=256-QAM、11ax(Wi-Fi 6)=1024-QAM、 11be(Wi-Fi 7)=4096-QAM。「新しい規格ほど速い」の中身の大部分はより密な点を打てるようになった (+チャネル幅拡大+多重化の改良)ことです。ただし密な変調はAPの近くでしか使えず、 距離が離れると自動的に粗い変調へ落ちます(レートアダプテーション)。壁の向こうで遅いのは仕様どおりの物理です。

L2隠れ端末問題 — 「お互い聞こえない2人」をAPが仲裁する

CSMA/CAは「送信前に聞く」が原則ですが、端末Aと端末BがどちらもAPには届くのに、互いの電波は聞こえない配置が起こります (部屋の両端など)。Aが送信中でもBには「静か」に聞こえるため、Bも送信してAP上で衝突——これが隠れ端末問題。 解決策が RTS/CTS です。

端末AAPには届く・Bは聞こえない
APAもBも聞こえる唯一の存在
端末BAPには届く・Aは聞こえない
① RTS「これだけの時間、送りたい」
② CTS「Aさんどうぞ」— Bにも聞こえる
Bは CTS 内の所要時間(NAV)ぶん自主的に沈黙
③ DATA — 衝突の心配なく送信
④ ACK — 受領確認(無線は必ずL2でACK)

ポイントは②:CTSはBにも届くので、Bは「今から誰かが使う」と知り、NAV(Network Allocation Vector)という カウントダウンタイマーの間は送信を控えます。聞こえない相手との調停を、両方から見える第三者(AP)の宣言で解決する設計です。

L2ローミング — 歩きながらAPを乗り換える(802.11k/v/r)

オフィスで会議室へ歩いても Webex 通話が切れないのは、端末がAPからAPへ「引っ越し」しているからです。 素朴にやると再スキャン+再認証で数百ms〜数秒切れますが、k/v/r の三点セットがこれを50ms以下に縮めます。

スマホ通話中・移動中
AP-1(今here)RSSI −72 dBm と劣化中
AP-2(会議室)同じSSID・同じ配線網
① 信号劣化を検知 — 引っ越し先を探し始める
② 802.11k Neighbor Report「近所のAP一覧ください」
③ 802.11v BSS Transition「AP-2 (ch44) がお勧めです」

企業無線の現場では: 実際のAP選択は端末側の実装に依存するため、インフラ側は バンドステアリング(5/6 GHzへ誘導)、最低データレート制限(遠くの端末を粘らせない)、 適切なAP配置とセル設計で「良い引っ越し」を誘導します。無線LANコントローラ(WLC)は 全APのチャネル・出力を俯瞰して自動調整し、ローミング時の鍵(PMK-R0/R1)を各APへ事前配布しておく—— これが 802.11r を成立させている裏方です。

Wi-Fi 6多数の端末を同時にさばく — OFDMA と MU-MIMO

これまでのCSMA/CAは「1本の廊下を1人ずつ順番に使う」時分割の世界でした。しかし1つのAPに数十台がぶら下がる 現代のオフィス・家庭では、この「順番待ち」自体がボトルネックになります。Wi-Fi 6(802.11ax)が持ち込んだ OFDMAとMU-MIMOは、この前提を「1人ずつ」から「複数同時」へ書き換えました。 下のボタンで、同じ4台ぶんの通信が方式によってどう変わるかを見比べてください。

3つの「分割」は足し算で効く: OFDMA は1つのチャネルを RU(リソースユニット)という細い周波数の短冊に割り、小さなパケットを持つ複数端末を 1回の送信機会に相乗りさせます(音声・IoT・既読通知のような小口通信に絶大)。 MU-MIMO は複数アンテナが作る電波の指向性(ビームフォーミング)で、 同じ時間・同じ周波数のまま別々の端末へ別々のデータを飛ばします(動画のような大口の下りに有効)。 さらに BSS Coloring が「隣家のAPの電波」に色を付けて自分宛でないと判れば送信を止めない—— と、Wi-Fi 6の高密度性能は時間・周波数・空間・識別の4方向の多重化の総合力です。 スケジューラを握るAP(親)の賢さがそのまま体感速度になる、というのが有線との決定的な違いです。

なぜ ① と ③ はブロードキャストなのか? ①の時点で PC は DHCP サーバの居場所を知らないため、宛先IP 255.255.255.255・ 宛先MAC ff:ff:ff:ff:ff:ff で LAN 全員に届けるしかありません。 ③がブロードキャストなのは、複数の DHCP サーバが OFFER を出した場合に 「私は 192.168.1.1 の提案を選びました」と選ばれなかったサーバにも通知するためです。 なお応答(②④)は実装により unicast / broadcast の両方があり得ます(クライアントの BROADCAST フラグに依存)。
Chapter 3 — ARP (RFC 826)

「192.168.1.1 さん、MACアドレス教えて」 — ARP

IPアドレスは分かっても、同一LAN内でフレームを届けるにはMACアドレスが必要です。 インターネット宛の通信では、最初の一歩は必ず「デフォルトゲートウェイ(ルータ)のMAC」宛。 これを解決するのが ARP です。▶ ボタンでブロードキャストの広がり方を再生できます。

Request は 全員に届くが、自分宛でないホスト(スマホ・TV)は黙って破棄。該当者だけが ユニキャストで返事をする。

ARP解決後、PCのARPテーブルはこうなる

IPアドレス192.168.1.1
MACアドレスa4:12:42:0e:9b:01
種別 / 保持dynamic(OSにより数十秒〜数時間キャッシュ。期限切れで再ARP)

Windowsなら arp -a、macOS/Linuxなら arp -a や ip neigh で今すぐ確認できます。 以後、インターネット宛のフレームはすべて「宛先MAC = このルータ」で送出されます。 なお IPv6 では ARP は使わず、ICMPv6 の近隣探索(NDP, RFC 4861)が同じ役割を担います。

Chapter 4 — L2 Switching

同じ島の中の配達員 — スイッチのMACアドレス学習

Chapter 5 — Routing

島の外へ出る判断 — 経路表と「最長一致」

宛先IPが自分と同じサブネットならARPして直送。外なら、ルータの経路表に委ねます。 経路表に複数の候補が一致した場合の鉄則がひとつだけ —— 最も具体的な(プレフィックスが長い)経路が勝つ(longest prefix match)。 宛先を選んで、ルータの頭の中を覗いてみてください。

この表は誰が書くのか? 直接接続(C)は自動、少数なら手書きの静的経路(S)。しかし社内数百、インターネットでは約100万経路ともなると 人手では不可能で、ルータ同士が経路情報を交換するルーティングプロトコル(社内=OSPF、インターネットの背骨=BGP)が経路表を育てます。 またルータはパケットを転送するたびに TTLを1減算し(0で破棄・ループ対策)、 Ch0で見たとおりL2ヘッダを次の区間用に貼り替えます。 出口ルータが単一障害点にならないよう、2台で仮想IPを共有する VRRP/HSRP という冗長化も実務では定番です。
Chapter 6 — NAT / NAPT (RFC 3022)

NATの副作用と限界: 表に載っていない外からの着信は行き先が分からず破棄されます — これが家庭を守ってきた「簡易ファイアウォール」効果 (裏返すと、サーバ公開にはポートフォワーディングが必要)。ポートは1つのIPあたり最大約6.4万で有限、 ISP側でさらに共有するCGN(キャリアグレードNAT)ではこの枯渇が現実問題になります。 そして端末が正真正銘のグローバルアドレスを持つIPv6ではNATは原則不要(Ch14)—— その代わり、遮断の仕事は明示的にファイアウォールが担うことになります。
Chapter 7 — Access Control List

途中には「関所」がある — ACL

パケットはルータやファイアウォールを通過するたびに検問を受けます。ACL は 送信元/宛先IP・プロトコル・ポート番号(いわゆる5タプル)を上から順に照合し、最初に一致したルールで即決する仕組みです。 どのルールにも一致しなければ、リストの最後に隠れている 暗黙のdeny(implicit deny) で破棄されます。 左のパケットをクリックして、審査の様子を見てください。

ip access-list extended INTERNET-OUT  (上から順に評価・first match)
10permit udp 192.168.1.0 0.0.0.255 any eq 53 DNS を許可
20permit tcp 192.168.1.0 0.0.0.255 any eq 443 HTTPS (TCP)
30permit udp 192.168.1.0 0.0.0.255 any eq 443 QUIC / HTTP/3
40deny tcp any any eq 23 log Telnet 禁止+記録
—deny ip any any  (暗黙のdeny・設定に書かれない)

← パケットを選ぶと、上から順に照合します

実務での落とし穴: ACLは 順序がすべて。広い permit を上に書くと、その下の細かい deny には永遠に到達しません。 また QUIC の普及で「TCP/443 だけ許可して UDP/443 を忘れる」と、ブラウザは自動で TCP へフォールバックするため 「遅いけど繋がる」という発見しづらい劣化が起きます。家庭ではルータの NAT +簡易FW、企業では ステートフルFWや Cisco の CoPP・ZBFW など、より文脈を見る仕組みへ発展していきますが、 「上から照合・最初の一致で即決・最後は暗黙のdeny」という原理はすべての土台です。
Chapter 8 — Watching YouTube

シナリオ①:YouTube を再生する

DHCP・ARPが済んだPCで、ブラウザに youtube.com と打ち込んで動画をクリックするまで。 現代のYouTubeは HTTP/3 = QUIC(UDP/443) 上で動きます。流れは大きく3幕です。

L7 DNS UDP/53 名前 → IPアドレス

ブラウザはまず OS のスタブリゾルバに問い合わせ、キャッシュに無ければ DHCP で教わった DNSサーバ(ここではルータ経由でISPのフルリゾルバ)へ UDP/53 のクエリを送ります。 フルリゾルバはルートサーバ → .com のTLDサーバ → Google の権威サーバ、と反復問い合わせで解決します。

応答はキャッシュされ、TTL(この例では300秒)の間は再問い合わせ不要。2回目以降の再生が速い理由のひとつ。
最近の実像: ChromeやスマホOSは DoH(DNS over HTTPS, TCP or QUICの443)で暗号化してDNSを引くことが増えており、 その場合ネットワーク側からはクエリ内容が見えません。また実際の動画データは youtube.com 本体ではなく、 解決の結果案内される *.googlevideo.com のCDNエッジ(ISP内のGGCキャッシュのことも)から届きます。

QUIC + TLS 1.3 UDP/443 たった1往復で暗号路を確立

従来のHTTPS(HTTP/2まで)は「TCPの3ウェイハンドシェイク → TLSハンドシェイク」と直列で2〜3往復(RTT)必要でした。 QUICは輸送の確立とTLS 1.3の鍵交換を同じ1往復に相乗りさせ、しかもUDP上に自前で再送・輻輳制御を実装しています。

ブラウザ (PC)192.168.1.23 : 51428
YouTubeフロントエンド172.217.175.110 : 443
① Initial: ClientHello + 鍵シェア (X25519)
② Initial/Handshake: ServerHello + 証明書 + Finished
③ Handshake: Finished ＋ もうHTTPリクエスト同梱可
④ HTTP/3: GET /watch?v=... (1-RTT データ)
⑤ HTTP/3: 200 OK — HTML/プレーヤーJS 多重ストリームで

QUICのすごさ: 再訪問なら 0-RTT(前回の鍵を再利用し、①と同時にGETを送る)まで可能。 さらにコネクションはIP/ポートでなくConnection IDで識別されるため、Wi-Fi→モバイル回線に切り替わっても再ハンドシェイク不要で再生が続きます(コネクションマイグレーション)。 HTTP/2で問題だった「TCPの1パケット欠落で全ストリームが待たされる」HoLブロッキングも、ストリーム独立再送で解消しています。

DASH / ABR 動画は「数秒ごとの断片」を選びながら落とす

プレーヤーはまずマニフェスト(どの画質のセグメントがどのURLにあるかの目録)を取得し、 以後は数秒ぶんの断片(セグメント)を Range 付き GET で次々に要求します。 映像(VP9/AV1)と音声(Opus)は別ストリームで、スループットの実測に応じて 次のセグメントの画質を毎回選び直す——これが ABR(Adaptive BitRate)です。

1080p・約5 Mbpsの動画なら、毎秒約420個(≒5,000,000 bit ÷ 8 ÷ 1,500 byte)のフルサイズ級パケットが届き続ける計算です。 サーバ側はISP内に置かれたキャッシュ(Google Global Cache)から配信されることが多く、往復遅延を数msまで縮めています。

現在の鍵交換(ECDH)と署名(ECDSA/RSA)の安全性は「離散対数・素因数分解が解けない」ことに依存しますが、 十分大きな量子コンピュータ上のShorのアルゴリズムはこれを多項式時間で解きます。 脅威は将来ではなく現在です——暗号化された通信を今のうちに録画しておき、量子機が完成してから復号する 「Harvest Now, Decrypt Later」が成立するからです。10年後も秘密であるべきデータは、今日から守る必要があります。

移行はもう始まっています: NISTが2024年に標準化した ML-KEM(FIPS 203・鍵交換)/ ML-DSA(FIPS 204・署名)/ SLH-DSA(FIPS 205・署名)を軸に、TLSでは上図のハイブリッド鍵交換 X25519MLKEM768 が Chrome・Cloudflare・主要CDNで既に既定有効化され、あなたの今日のHTTPSの一部はすでに耐量子です。 一方で署名(証明書チェーン)側の移行はこれから——鍵・署名サイズが大きく、 ハンドシェイクのパケット数やMTU(Ch13!)に跳ね返るためです。設計者への教訓はひとつ: アルゴリズムを差し替え可能にしておく暗号アジリティ(crypto agility)が、次の30年の必須要件です。

認証の数学なぜ WPA3 はパスワード総当たりに強いのか — SAE vs WPA2

Ch1で「SAEはパスワードを電波に流さない」と触れました。ここが WPA2 と WPA3 の決定的な差です。 両者の握手を攻撃者の視点で並べると、なぜ WPA2 が「録音してオフラインで総当たり」に弱く、 WPA3 がそれを封じたのかが見えます。下のボタンで切り替えてください。

核心はここ: WPA2 では、握手を1回盗聴して記録するだけで、攻撃者は手元のPCで 「パスワード候補 → 鍵を計算 → 記録したMICと一致するか」を好きなだけ高速に試せます(オフライン辞書攻撃)。 弱いパスフレーズなら数時間で陥落します。WPA3のSAEは PAKE(Password-Authenticated Key Exchange) の一種で、 1回の推測を試すのに必ずAPと1往復の通信が必要な設計(=オフラインで試せない)。しかも各セッションは 前方秘匿性(PFS)を持ち、将来パスワードが漏れても過去の通信は復号できません。 「盗聴を記録しても、後からの総当たりが原理的に効かない」——これがSAEの防御の本体です。

TLS 1.3「暗号レコード」の中身 — 握手のあと、本文はどう流れるか

Ch8で握手(1-RTTで鍵合意)を見ました。その後の全データは TLSレコード という単位で運ばれます。 TLS 1.3のレコードはAEAD(認証付き暗号)で守られ、一見ただのTCP/UDPペイロードにしか見えません。

レコードの部品中身攻撃者から見えるか
Content Type (外側)TLS 1.3では全て application_data(23) に偽装。真の種別は暗号内部に隠す見える(が無意味)
Length暗号文の長さ。ここからパケットサイズが漏れるため、パディングで隠す実装もある見える
暗号化ペイロード本文 + 真のContent Type。AES-GCM または ChaCha20-Poly1305 で暗号化×(鍵が必要)
AEAD 認証タグ (16B)改ざんされていれば復号が失敗する。暗号化と完全性検証が一体検証は受信者のみ
Nonce (暗黙)レコード連番から生成。同じ鍵で同じNonceを二度使わない(GCMの致命的禁忌の回避)送信されない

重要なのは、TLS 1.3では握手の途中(ServerHello以降)からもう暗号化が始まる点です。証明書すら暗号化されて運ばれるため、 経路上の盗聴者に「どのサイトの証明書か」すら基本的に見えません(SNIは例外だがECHで隠せる—Ch10)。 TLS 1.2までの「証明書は平文で見えていた」時代とはここが根本的に違います。

現代の設計思想「内側なら信じる」をやめる — ゼロトラストとマイクロセグメンテーション

ここまでの防御の多くは「LANの内側は比較的安全、境界(ファイアウォール)で守る」という境界防御の発想でした。 しかしクラウド・在宅・持ち込み端末が当たり前になり、「内側」という概念自体が溶けています。そこで主流化したのが ゼロトラスト——「ネットワークの位置では信用を判断しない。すべてのアクセスを、その都度、検証する」という原則です。

Chapter 11 — TCP Reliability (RFC 9293)

届くまで諦めない — TCPの信頼性メカニズム

IPは「届く努力はするが保証しない」。その上で順序どおり・欠けなく・詰まらせずを実現するのがTCPです。 仕掛けは4つ —— バイト単位の通し番号、確認応答(ACK)、再送、 そして自分から減速する自制心(輻輳制御)。パケットが1つ消える瞬間を含めて、ステッパーで追います。

スマホ (送信側)ISN=1000(乱数) / MSS 1460
サーバ (受信側)ISN=7000(乱数)
① SYN (seq=1000, MSS=1460, SACK OK)
② SYN/ACK (seq=7000, ack=1001)
③ ACK (ack=7001) — 接続確立
④ データ1460B×3 (seq=1001 / 2461 / 3921)
⑤ 2通目が消失! → ACK=2461 が3回続く(重複ACK)
⑥ Fast Retransmit — seq=2461 だけ即再送

輻輳制御のこころ:「損失=道が混んでいる合図」と解釈して自分から減速する。実際のLinuxはCUBIC、YouTube系はBBRという改良版で同じ思想を実装
2つの「待った」は別物: フロー制御(rwnd)は「受信側のバッファが溢れないように」、 輻輳制御(cwnd)は「途中のネットワークを詰まらせないように」。 実際に送ってよい量は min(rwnd, cwnd) です。 世界中のTCPがこの自制を守っているから、誰も全体を管理していないインターネットが崩壊せずに済んでいます —— そしてこの資産一式をUDPの上に持ち込み、進化させたのがCh8のQUICでした。
